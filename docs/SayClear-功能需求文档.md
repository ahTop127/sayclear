## 2. 产品定义与第一期边界

### 2.1 一句话定义

用户对着电脑**说话**表达需求；**SayClear** 把口语整理成「真正想说的内容」，填进**当前任意输入框**，供用户自己检查后发送或搜索。

SayClear 是一层智能输入，不是普通语音转文字，也不是聊天或搜索产品本身。流程：自然表达 → 智能整理 → 结构化输入 → 用户正在用的 AI / 搜索 / 其它输入框。

### 2.2 第一期形态（已定）

| 项 | 已定 |
|---|---|
| 形态 | Mac 桌面**悬浮工具** |
| 不是 | 浏览器插件、系统输入法、独立网页、手机端、Windows |
| 入口 | **全局快捷键 Command（⌘）**开始 / 结束录音。使用 Command，**不用 Ctrl** |
| 按键方式 | **单击切换**：按下一次开始录音，再按一次结束录音（不是按住）。第一期按键已指定为 Command |
| 输入方式 | **只有录音**。不支持打字、粘贴乱口语再整理 |
| 完成后 | 整理结果**直接填入当前输入框**，默认不弹出确认层，**也不弹出成功提示** |
| 发送 | **不代发**（不自动按回车 / 发送） |
| 不满意 | **在目标输入框里直接改字**。第一期**不做**「打开修改」悬浮层，也**没有**第二套修改快捷键 |
| 语言 | 中文、英文、**中英混合**都要能用 |
| 五个功能 | **全部上线**：语义清洗、智能纠错、智能分点、智能格式化、意图确认 |
| 输出策略 | **同一套整理逻辑**，不识别当前是 AI 还是搜索，**不要两套模板** |

### 2.3 口述如何被处理（已定，产品语言）

第一期通过**外部识别 / 整理服务**完成两件事：

1. 语音 → 文字  
2. 文字 → 结构化结果（清洗、纠错、分点、格式化、锁定意图）

**用户接受把口述发给这些服务。** 这不是「是否允许内容离开本机」的隐私选择题，也不是可开关的本机 / 外传模式。使用 SayClear，即按上述方式处理口述。

本文不指定服务商、接口或部署方式。功能规格不依赖「必须全部在本机完成」，也不把外传写成用户可选项。

识别或整理服务不可用、超时、返回失败时，按第 8 节失败态处理，不把半成品填进输入框。

### 2.4 输出原则（已定）

- 填入的是**已锁定意图的正文**，不是「我理解你的需求是……」这类确认话术。
- 多个并列需求或步骤 → **分点**。
- 一件事或一段连贯叙述 → **通顺段落**，不强行分点。
- 任意输入框用同一套规则。

## 3. 用户与场景

### 3.1 目标用户（已定）

高频使用 AI 工具和搜索引擎的学生、产品经理、开发者及其他知识工作者。

### 3.2 要解决的问题（已定）

说话时有口头禅、重复、停顿、自我纠正、顺序混乱。直接转成文字后：冗余、前后矛盾、多需求混杂、用户不知道有没有被听懂，只能反复改输入。

### 3.3 主路径（已定）

用户把光标放在任意输入框 → 按 **⌘** 开始说话 → 出现暗黑圆角录音条（左 X、中间波形、右 OK）→ 再按 ⌘ 或点 OK 结束 → 看到 **Thinking** → 整理后的正文出现在该输入框（无成功提示，悬浮层收起）→ 用户自己检查、按需在该输入框改几个字 → 自己按回车或点击发送。

录音中途点 **X**：取消这次说话，不填入、作废。第一期若要改字，只在目标输入框里改，没有「打开修改」。

### 3.4 具体场景

下列「说话原文」是口语示意；「期望输出」是填入输入框的正文。不论当前是 AI 对话框、搜索框还是备忘录，规则相同。

#### 场景 A：改口后的单一请求（段落）

- **说话原文：** 「帮我写一个 Python 脚本，不对，用 TypeScript，读取 CSV 然后，呃，输出 JSON。」
- **期望输出：** 「写一个 TypeScript 脚本，读取 CSV 并输出 JSON。」
- **要点：** 纠错保留最终版本；清洗掉「不对 / 呃」；只有一件事，不分点。

#### 场景 B：多个并列改点（分点）

- **说话原文：** 「这个页面有几个地方需要改，按钮太大了，颜色也需要调整一下，然后整体再简洁一点。」
- **期望输出：**
  1. 缩小按钮尺寸
  2. 调整页面颜色
  3. 简化整体页面设计
- **要点：** 多条并列需求，分点；去掉「有几个地方需要改」这类空壳套话。

#### 场景 C：中英混合

- **说话原文：** 「把这个 button 改小一点，再把 padding 调一下，那个 hover 状态的颜色太暗了。」
- **期望输出：**
  1. 把 button 改小
  2. 调整 padding
  3. 把 hover 状态的颜色调亮
- **要点：** 专有词 / 代码词保持原样；中英混在同一段口述里也能整理。

#### 场景 D：有顺序的多步（分点）

- **说话原文：** 「明天上午先去超市，然后下午去图书馆，晚上回来把报告写完。」
- **期望输出：**
  1. 上午：去超市
  2. 下午：去图书馆
  3. 晚上：完成报告
- **要点：** 多个步骤，分点；保留时间顺序。不因为「可能是搜索」就压成一句查询。

#### 场景 E：本来就是一句完整问题（段落）

- **说话原文：** 「嗯那个，帮我查一下 2024 年 WWDC 发布了哪些 AI 功能。」
- **期望输出：** 「查一下 2024 年 WWDC 发布了哪些 AI 功能。」
- **要点：** 一件事，通顺一句即可。不套 Prompt 模板，也不改成另一种「搜索专用」句式。

## 4. 主流程（用户逐步看到什么、可以做什么）

以下从用户视角写。状态名称可改文案，行为不可缺。

### 4.1 开始前

- 悬浮工具在后台可用（具体是否常驻屏幕：**待确认**外观，但不影响快捷键可用）。
- 用户先把光标放进想填入的输入框。产品**不**替用户选择 App，也**不**判断这是不是 AI 或搜索。

### 4.2 开始录音

- 用户按下全局快捷键 **Command（⌘）**。第一期按键已指定为 Command，不用 Ctrl。
- 按键方式（已定）：**按下一次开始、再按一次结束**（单击切换）。用户未要求按住；当前按单击理解。
- 用户看到：暗黑、圆角的录音条，明确正在录音。布局为 **[ X ]  [波形条纹…]  [ OK ]**。中间是语音波形条纹（随说话起伏）。
- 用户可以：继续对着电脑说话；再按 ⌘ 结束；或点录音条上的 **OK** 结束（与再按 ⌘ 同类）；或点 **X** 取消这次说话（不填入、作废，输入框保持原样）。
- 用户此时**不能**：打字或粘贴一段话让产品整理（第一期无此入口）。

### 4.3 结束录音

- 用户再按 ⌘，或点录音条上的 OK。
- 用户看到：录音结束，进入识别 / 整理。悬浮层**只显示 Thinking**，不要「正在整理，请稍后」这类话。不打断当前 App 的操作焦点去弹确认窗。
- 用户可以：等待。第一期不要求在整理中途预览逐字稿。

### 4.4 整理完成并填入

- 五个功能按第 6 节流水线处理完毕后，得到**锁定意图后的正文**。
- SayClear 把该正文填入**当前可填入的输入框**。
- 不弹「是否确认」层，不自动发送，**也不弹出「已填入当前输入框」之类成功提示**。
- 用户看到：输入框里出现整理后文本；SayClear 悬浮层收起或回到很克制的状态（平时几乎看不见）。
- 用户可以：直接在该输入框里改字；自己发送。

### 4.5 不满意时修改

填入后若要改字：**直接在目标输入框里改**。第一期不做悬浮层再编辑、不做「打开修改」快捷键。见第 7 节。

### 4.6 失败时

不填入错误正文或半成品。见第 8 节。用户可稍后重录。

## 5. 功能规格

五个功能第一期**全部交付**。它们是同一条整理链上的步骤，不是五个独立产品。是否允许用户单独开关某一步：见第 6 节与第 11 节（**待确认**）。

共同输入：一次录音被转成的文字（用户不可见中间稿也可以，第一期不要求展示原文）。  
共同输出：进入下一步的文本；最后一步产出填入输入框的正文。

### 5.1 语义清洗

#### 目的

去掉口头禅、无意义重复、卡顿和垫话，留下真正要说的信息。

#### 触发条件

每次成功得到转写文字后，作为流水线的一步自动执行。用户无需单独点「清洗」。

#### 输入 / 输出

- 输入：转写后的口语文本（可含中英混合）。
- 输出：信息完整、读起来干净的文本，尚未决定是否分点。

#### 处理规则

| 处理 | 规则 |
|---|---|
| 删除 | 口头禅与垫话，如「嗯、啊、那个、就是、你知道吧」以及明显无意义的停顿残留 |
| 删除 | 同一意思的机械重复（「就是，就是」） |
| 保留 | 用户真正提出的对象、动作、条件、数字、专有名词、代码标识符、英文术语 |
| 保留 | 表示顺序或逻辑的「然后 / 但是 / 因为」，若删掉会丢顺序或因果关系 |
| 不新增 | 用户没说过的需求、背景、角色设定、输出格式要求 |
| 不改成话术 | 不把内容改写成「请作为资深专家……」之类套话 |

程度副词（如「稍微」）和情绪词是否一律保留：**待确认**。在拍板前，默认**不因为「更专业」而删掉程度和语气**；只删确定没有信息量的垫话。

#### 正向例子

| 输入（示意） | 输出（示意） |
|---|---|
| 「嗯，我觉得这个页面吧，就是，就是有点复杂，我希望它能稍微简洁一点。」 | 「我希望这个页面整体更加简洁。」（若保留「稍微」，则为「稍微简洁一点」——程度词待确认） |

#### 边界例子

| 情况 | 输入（示意） | 期望 |
|---|---|---|
| 只有一句 | 「把标题改成产品介绍」 | 通顺一句，不扩写 |
| 中英混合 | 「把 API timeout 调到 30 秒」 | 保留 `API`、`timeout`、`30` |
| 数字 / 代码 / 专有名词 | 「用 React 18，不要 Vue」 | 名称与版本原样保留（纠错另见 5.2） |
| 空壳套话 | 「我有个需求就是吧……」（后面还有实质） | 去掉套话，留实质 |
| 极长口述 | 连续说很多句，信息都相关 | 清洗垫话，不擅自摘要到丢失条目；过长截断策略见待确认 |

#### 验收

- Given 转写含口头禅和重复，When 清洗完成，Then 输出中不再出现这些垫话，且原需求对象仍在。
- Given 转写含函数名、数字、英文术语，When 清洗完成，Then 这些片段未被翻译、改写或删除。
- Given 用户只说了一句完整需求，When 清洗完成，Then 不因此拆成多条，也不添加用户未说的约束。

### 5.2 智能纠错（自我修改）

#### 目的

识别说话过程中的自我修改，**只保留最终版本**，丢掉被否定的旧说法。

#### 触发条件

流水线中自动执行。不单独入口。

#### 输入 / 输出

- 输入：通常为清洗前或清洗中的文本（与清洗的先后见第 6 节）。
- 输出：前后矛盾已按「最后意图」收拢的文本。

#### 处理规则

| 处理 | 规则 |
|---|---|
| 覆盖 | 明确改口：如「不对 / 算了 / 不是……是…… / 改成 / 还是……吧」，保留后说的版本，删除被推翻的版本 |
| 保留补充 | 后说的是补充而非替代时（如先说「改按钮」，再说「对了，文案也要改」），两条都留 |
| 不猜测 | 没有改口或补充信号、只是说得不清楚时，不擅自删掉前半句「可能过时」的内容 |

如何更稳地区分「补充」和「覆盖」，尤其是没有「算了 / 不对」等词时：**待确认**更细规则。拍板前：有明确否定 / 替换信号则覆盖；明显是新增对象则补充；其余从宽保留，避免误删。

#### 正向例子

| 输入（示意） | 输出（示意） |
|---|---|
| 「我 3 点去值机……算了，我还是 5 点去值机。」 | 「我 5 点去值机。」 |
| 「帮我写一个 Python 脚本，不对，用 TypeScript」 | 只保留 TypeScript 方案 |

#### 边界例子

| 情况 | 输入（示意） | 期望 |
|---|---|---|
| 补充而非覆盖 | 「先改按钮。对了，标题也改一下。」 | 按钮和标题都保留 |
| 多次改口 | 「用红色，不对蓝色，还是黑色吧」 | 只留黑色 |
| 中英混合改口 | 「用 fetch，不对，用 axios」 | 只留 axios |
| 无转折词、两句并列 | 「按钮太大了。颜色也不对。」 | 视为两条需求，不覆盖 |

#### 验收

- Given 口述先提出 A 再明确改成 B，When 纠错完成，Then 输出含 B 不含 A。
- Given 口述在已有需求上追加另一对象，When 纠错完成，Then 两者都在。
- Given 无改口信号的并列槽点，When 纠错完成，Then 不把后一句当成对前一句的覆盖。

### 5.3 智能分点

#### 目的

把混在一起的多个需求或步骤，整理成清晰的 1、2、3。

#### 触发条件

流水线自动判断：存在**多个并列需求或步骤**时分点；只有一件事或连贯叙述时不分点，交给格式化走段落。

#### 输入 / 输出

- 输入：清洗并纠错后的文本。
- 输出：若干条并列条目，或「仍是一段、无需分点」的说明性结果（由格式化最终落成段落）。

#### 处理规则

| 处理 | 规则 |
|---|---|
| 要分点 | 两个及以上互相独立的需求、问题、修改点、步骤 |
| 不分点 | 单一请求；一句完整问题；前后句是同一件事的修饰 / 原因 |
| 一条一点 | 每条只表达一个可执行意思，去掉「另外就是还有就是」 |
| 可轻度改写 | 允许把「按钮太大了」收成「缩小按钮尺寸」这种**同义、更利落**的条目，但不得改成相反或额外需求 |
| 不按 App 分模版 | 不因「这像搜索」就把多条压成一句，也不因「这像 Prompt」而加角色设定 |

主需求与约束混在一句里时（如「把按钮改小，但别动布局」）：能拆成「改按钮」+「保持布局」则拆；约束只修饰同一动作则留在同一条。含糊时**待确认**更细规则，拍板前优先不拆丢约束。

#### 正向例子

见场景 B、C、D。

#### 边界例子

| 情况 | 期望 |
|---|---|
| 只有一句 | 不分点 |
| 搜索问句但含三件要查的事 | 若确是并列查询点，仍分点；若是一个问题，段落 |
| 「先…再…最后…」 | 分点，并保留顺序 |
| 一条很长但其实是一件事 | 不分点，避免假清单 |

#### 验收

- Given 口述含三个独立改点，When 分点完成，Then 输出三条，且每条能对应原意。
- Given 口述只是一个完整问题，When 分点判断完成，Then 不产出 1、2、3。
- Given 分点发生改写，When 对照原意，Then 没有新增未提及的需求，也没有把否定改成肯定。

### 5.4 智能格式化

#### 目的

按内容选择形态：**分点清单**或**通顺段落**。让填进任意输入框的文字可直接用。

#### 触发条件

流水线最后成形时自动执行。无「Prompt 模板 / 搜索模板」切换。

#### 输入 / 输出

- 输入：已清洗、纠错、并完成是否分点的判断（及条目）。
- 输出：最终正文（纯文本结构：段落，或 `1. 2. 3.` 式分点）。

#### 处理规则（已定）

| 内容形态 | 输出 |
|---|---|
| 多个并列需求或步骤 | 分点（建议用 `1. 2. 3.`，任意输入框都能读） |
| 一件事，或连贯叙述 | 通顺段落 / 一两句完整话，**不强行分点** |

补充规则：

- **同一套逻辑**用于任意输入框，不识别当前 App。
- 不输出「我理解你的需求是：」前缀，不输出「以下是给你的 Prompt：」。
- 第一期不要求 Markdown 勾选框、表格、代码围栏等富格式（是否对「本身在口述代码」保留代码换行：**待确认**；拍板前以可读纯文本为准，代码标识符仍原样保留）。
- 「任务清单」不作为第三套模板：有多步就分点并保留顺序 / 时间；只有一件待办就一段话。

#### 正向例子

- 场景 B/C/D → 分点。  
- 场景 A/E → 段落。

#### 边界例子

| 情况 | 期望 |
|---|---|
| 两件小事 | 分点，不要硬写成一句很长的并列句（除非用户原话就是一句且拆开会伤原意） |
| 一件事但说了原因 | 一段话，不要「1. 需求 2. 原因」除非用户明确当两条 |
| 对着搜索框说了三条改 UI 的需求 | 仍分点，不压成关键词串 |

#### 验收

- Given 多条并列需求，When 格式化完成，Then 填入文本为分点，且无确认话术前缀。
- Given 单一连贯请求，When 格式化完成，Then 填入文本为段落，没有无意义的 `1.`。
- Given 同一段口述，When 分别想象填入 AI 框或搜索框，Then 正文相同。

---

### 5.5 意图确认

#### 目的

从口语里抽出并**锁定**用户真正想说的内容，避免把被改掉的旧说法、垫话、混杂需求原样送进输入框。

#### 触发条件

每次整理的最后一步自动发生。第一期**默认不弹确认层**。

#### 输入 / 输出

- 输入：前面各步已整理的内容。
- 输出：锁定后的正文 → **直接填入当前输入框**。

#### 处理规则（已定交互）

| 做 | 不做 |
|---|---|
| 锁定最终意图后再填入 | 不先弹窗问「这是你的意思吗？」 |
| 填入可用正文 | 不填「我理解你的需求是……」 |
| 不代发 | 不替用户按回车 / 发送 |
| 填入后可在输入框改字 | 不弹成功提示；不把修改做成必须先确认才能填入；第一期不做「打开修改」 |

意图确认在第一期的含义是：**整理链必须收敛到最终意图**，用户用输入框里的正文做事后确认，而不是事前拦截。

#### 正向例子

- 介绍里的确认稿「我理解你的需求是：1. 优化页面……」**不得**作为填入内容。  
- 应填入与 5.3/5.4 一致的正文列表或段落。

#### 边界例子

| 情况 | 期望 |
|---|---|
| 用户立刻自己改输入框 | 允许；产品不抢焦点弹层 |
| 用户想改刚填入的正文 | 在目标输入框里直接改；无悬浮层编辑 |
| 锁定后仍有歧义 | 仍填入当前最佳锁定结果，不改成向用户提问的句子（第一期不在输入框里反向提问） |

#### 验收

- Given 整理成功，When 填入发生，Then 输入框中是锁定后的正文，且没有确认话术。
- Given 整理成功，When 观察系统动作，Then 没有自动发送。
- Given 用户未再打开任何 SayClear 层，When 填入完成，Then 没有成功提示条，也没有额外确认窗挡住输入。

## 6. 五个功能如何串成一条流水线

### 6.1 顺序（第一期默认）

建议固定为一条链，用户无感知分步：

1. 语音 → 文字（外部识别服务）  
2. **智能纠错**（先按最终说法收拢，避免清洗误删改口信号）  
3. **语义清洗**  
4. **智能分点**（判断该不该拆、怎么拆）  
5. **智能格式化**（段落或分点落成正文）  
6. **意图确认**（锁定正文并填入，无确认弹层）

若实现上纠错与清洗一次完成，对外仍必须同时满足第 5 节各条规则。本文不规定内部如何调用服务。

### 6.2 开关

- **已定：** 第一期五个功能都要做，不能只上其中几个。  
- **待确认：** 用户是否可以单独关掉某一步（例如「不要分点」）。未确认前，**默认全部生效，无设置项。**

### 6.3 与输入框类型无关

整条链只产出一套正文。不因目标是 AI 还是搜索而分支。

---

## 7. 填入后如何改字

### 7.1 默认行为（已定）

整理成功 → 直接填入目标输入框 → 不代发 → **不弹出成功提示**。用户不满意 → **在该输入框里直接改字**。

第一期**不做**：

- 「打开修改」快捷键
- 悬浮层再编辑再写回
- 历史列表、多条会话回看

意图确认的事后确认 = 用户看输入框里的正文，自己改、自己发送。

### 7.2 取消这次说话（已定）

录音尚未结束时，点录音条上的 **X**：这次说话作废，不进入识别 / 整理，不把任何内容填入输入框。输入框保持取消前的样子。用户可稍后按 ⌘ 再录。

---

## 8. 快捷键与悬浮层（用户可见行为）

第一期录音快捷键 **已指定为 Command（⌘）**，使用 Command，不用 Ctrl。方式为单击切换：未在录音时按一次 → 开始录音；录音中再按一次 → 结束并进入 Thinking。

| 作用 | 行为 |
|---|---|
| 开始 / 结束录音（⌘） | 未在录音时按下 → 开始录音；录音中按下 → 结束并进入识别 / 整理（与点 OK 同类） |
| 录音条上的 OK | 结束本次录音并进入 Thinking（与再按 ⌘ 同类） |
| 录音条上的 X | 取消这次说话：不识别、不填入、输入框不变 |

第一期**没有**「打开修改」快捷键。⌘ 会不会和系统或其它 App 的快捷键冲突：**待确认**（按键本身已定）。

### 8.1 录音中

- 明确表示正在录音：暗黑、圆角的录音条，中间为语音波形条纹。
- 布局：**[ X ]  [波形条纹…]  [ OK ]**。不要方形控件。
- 不把未完成的半句填进输入框。
- 不代发。
- 用户说话被交给外部识别 / 整理服务处理（用户已接受）；过程中不必展示服务名称。

### 8.2 识别 / 整理中（Thinking）

- 悬浮层**只显示 Thinking**。不要「正在整理，请稍后」这类话。
- 不弹确认层。
- 整理完成前不填入，避免先填原文再闪成整理稿（是否允许极短过渡文案：**待确认**，默认不要闪两截不同正文）。

整理中途再按 ⌘：是取消本次，还是不允许打断，**待确认**。未确认前建议：整理中忽略新的开始录音，或保持 Thinking（二选一待拍板）。

### 8.3 成功

- 正文出现在输入框。
- **没有**成功提示条（不要「已填入当前输入框」）。
- SayClear 悬浮层收起或回到很克制的状态。
- 立刻允许用户在输入框里改字。

### 8.4 失败态（必须可区分）

失败时：**不代发、不填入乱码或明显未完成稿**。悬浮层用短句说明原因和用户下一步（通常是：授权后重试 / 再录一次 / 点一下输入框后再试）。

| 失败 | 用户能理解的含义 | 用户可以做什么 |
|---|---|---|
| 没有麦克风权限 | 无法录音，因为系统未允许使用麦克风 | 去打开麦克风权限后重试 |
| 没录到声音 | 这段录音里没有可用的说话内容（过短、静音、几乎无语音） | 靠近再录一次 |
| 整理失败 | 识别或整理没成功（含外部服务失败、超时、返回不可用结果） | 稍后重试；不把失败信息当正文填入 |
| 当前没有可填入的输入框 | 整理成功了，但现在没有能接收文字的输入位置 | 点进一个输入框后重试或重录（写入重试方式待确认） |
| 填入失败 | 有输入框，但这次没能把文字放进去 | 明确告知失败；用户可稍后重录（是否提供可拷贝文稿待确认） |

不在失败文案里写系统接口名称、权限项技术名。

录音开始时已无麦克风权限：应立刻失败，不要假装在录音。

## 9. 输出形态规则（汇总）

| 规则 | 已定 |
|---|---|
| 填入内容 | 锁定意图后的正文 |
| 禁止填入 | 「我理解你的需求是……」及同类确认 / 角色扮演套话 |

| 一件事或连贯叙述 | 通顺段落，不强行分点 |

## 11. 待确认问题清单

供拍板；下列**不是**已定需求。

1. **填入时机与焦点：** 录音结束到整理完成之间，用户换了输入框或切了 App，文字填进「结束录音时」还是「完成时当前」的框？  
2. **Thinking 时再按 ⌘：** 取消本次，还是忽略并保持 Thinking？  
3. **⌘ 与系统冲突：** 按键本身已定为 Command 单击切换；会不会和系统或其它 App 的快捷键冲突、要不要加修饰键，仍待确认。  
4. **悬浮层外观：** 是否始终可见一小块，还是仅录音 / Thinking / 失败时出现？  
5. **功能开关：** 五个功能全部交付，但是否允许用户关掉其中一步？  
6. **程度词与语气：** 「稍微」类副词、情绪词默认保留还是可去掉？  
7. **无标记改口：** 没有「不对 / 算了」时，覆盖还是从宽都保留？  
8. **极长口述：** 是否截断、如何提示「过长请分段说」？  
9. **填入失败后：** 点进输入框后如何重试；失败时是否提供可拷贝文稿？  

已从待确认中删除、现为已定的包括：平台仅 Mac；仅快捷键录音；快捷键为 Command（⌘）单击切换（不用 Ctrl）；不代发；直接填入且无成功提示；五功能全上；不支持打字粘贴；不区分 Prompt / 搜索；口述交给外部识别与整理服务（不是本机 / 外传选择题）；录音条为暗黑圆角 + 波形 + 左 X 右 OK；整理中只显示 Thinking；第一期不做「打开修改」；要改字在目标输入框直接改。
